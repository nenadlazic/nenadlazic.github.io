Anti-piracy at the CDN edge: the door you check once

August 17, 2026

—

Your egress bill is growing faster than your subscriber count. Nothing is broken. No alert fired. Authorization is working exactly as designed, every request in the access log is well formed, and the ratio of bytes served to accounts billed keeps drifting in the wrong direction.

This is a post about protecting delivery at the CDN edge. Not about protecting content - that is a different problem with different tools. This is about the plainer question of who is consuming your delivery capacity, and why the usual answer is “we authorize at the start of a session and hope”.

The shape of the problem

Take a typical segmented delivery flow. A client asks for a stream or a large asset, you authorize it, and you hand back a manifest. The client then fetches segments for the next two hours.

  GET /session?...        -> full authorization: entitlement, geo,
                             concurrency, credentials, device
                          -> issue session id, return manifest

  GET /variant.m3u8       -> does this session id exist? yes -> serve
  GET /segment_0001.ts    -> serve
  GET /segment_0002.ts    -> serve
  ...
  GET /segment_3600.ts    -> serve

One request is authorized. Several thousand are served on the strength of that decision. That ratio is the entire security posture, and it is worth staring at for a moment: 99.97% of the requests, and effectively 100% of the bytes, are delivered by a code path that checks nothing.

The session id in that flow is a bearer credential. Whoever holds it gets the bytes. It is usually a random string in a query parameter or a cookie, it is usually not bound to anything, and it usually outlives the authorization that produced it.

This is not an implementation bug. It is a deliberate design that made sense when the threat model was “someone who did not pay”. Against that threat it works. The problem is that the abuse which actually costs money looks nothing like that.

Three consumers you are paying for

  • Shared credentials. One account, many people. Concurrency limits address this, badly, and only if they count the right thing.
  • Leeching. A third party serves their own audience directly from your edge. Their users hit your CDN, your egress, your cache.
  • A reimplemented client. Someone reverse engineers your player or app, and their client talks to your edge with valid credentials obtained through your real login.

None of these are unauthenticated. Every one of them presents something legitimate. That is the whole difficulty: your authorization layer is being asked a question it answers correctly, and the correct answer is the wrong outcome.

What a request can actually prove

Before designing anything, it is worth being brutally clear about which parts of an incoming request are evidence and which parts are decoration.

Everything the caller sends, the caller chose. That includes far more than people assume.

Signal Spoof cost for a motivated caller
User-Agent One line of code
Header set, count, values Copy from a real client capture
Header order and casing Moderate - needs a patched HTTP stack
HTTP/2 SETTINGS, WINDOW_UPDATE, pseudo-header order Moderate to hard
TLS ClientHello fingerprint (JA3 / JA4) Low, with off-the-shelf tooling
Request cadence and playback behaviour High, but not impossible
Source IP address Not possible over TCP

Two entries on that list deserve elaboration.

TLS fingerprinting is weaker than its reputation

JA3 was a genuinely useful signal until Chromium shipped ClientHello extension order permutation, randomized per connection, which showed up in the wild in January 2023. With roughly fifteen permutable extensions, essentially every Chrome connection produces a distinct JA3. Cipher stunting had already made the point earlier: Akamai reported distinct JA3 values going from about 18,600 to roughly 1.355 billion in six months, driven by a tool that randomized the cipher list.

JA4 fixes the collection problem by sorting the cipher and extension lists before hashing, which is why it survived both. What it does not fix is the underlying issue: tooling like uTLS and curl-impersonate will reproduce a target’s TLS fingerprint, HTTP/2 fingerprint and header order simultaneously. A perfect browser fingerprint proves that the caller links against a particular TLS library. Nothing more.

There is also a scale problem that gets glossed over. Cloudflare has published roughly 15 million distinct JA4 fingerprints against 500 million user agents and billions of IPs. A head fingerprint covers hundreds of millions of devices. A fingerprint is a software classifier, not an identity, and its anonymity set ranges from millions of devices down to a handful depending on how exotic the client is.

The source IP is the one thing that cannot be invented

Over TCP, source address spoofing does not survive the handshake. Spoof the source and the SYN-ACK is routed to the address you claimed, not to you. You never complete the handshake, you never receive a byte. QUIC has address validation with the same effect.

So every request you have actually served came from a routable address at which the caller genuinely receives packets. In a stack where everything else is self-declared, that is a rare and valuable property.

Which is exactly why the application layer usually throws it away.

The X-Forwarded-For trap

Network-level spoofing is impossible. Application-level spoofing is trivial if you trust a forwarding header without checking who set it. Any origin that does remoteIp = header("X-Forwarded-For") has handed the caller a free IP-spoofing primitive, and this is one of the most common serious misconfigurations in delivery stacks.

The correct shape is a trust gate on the transport peer:

IpAddress remoteIp() {
    if (isLocalhost(tcpPeer())) {          // only a local reverse proxy
        IpAddress fromHeader = xForwardedFor();
        if (fromHeader != null) return fromHeader;
    }
    return tcpPeer();                      // otherwise, the real peer
}

The mirror-image failure is just as damaging and much easier to ship by accident. If your load balancer terminates TCP and is not on loopback, the gate rejects the header, and every request now appears to originate from the load balancer. You have not been spoofed. You have simply lost the only trustworthy field in the request, and every design in the rest of this post silently stops working.

Whichever way you resolve it, resolve it explicitly and assert it in a test.

Counting the right thing

Here is where most designs go wrong, and it is a counting error rather than a cryptographic one.

The instinct is to treat the fingerprint as an identifier and block on it. That is backwards. Consider what is normal:

  many IPs sharing one fingerprint    -> completely normal
                                         a fingerprint is a device class;
                                         tens of thousands of real users
                                         share one

  many IPs on one session id          -> not normal
                                         a real session sees 1 to 3 addresses
                                         over its life; a shared credential
                                         sees dozens within minutes

  fingerprint changing within a
  single session                      -> almost never normal

The third rule is the highest-signal, lowest-false-positive check available, and almost nobody implements it. It costs one comparison per request against state you already hold.

It also has one caveat that will bite on day one. On Android, an application commonly fetches the manifest with its own HTTP client and lets the media player fetch segments through a different data source, with a different header set. iOS behaves similarly. So the invariant is not “one fingerprint per session” but one expected fingerprint per request class - manifest, segment, key - compared only within its class. Get this wrong and you will drop legitimate clients on their first segment.

The general principle: identity is the account or token, the IP is the anchor of truth, and the fingerprint is a tripwire that must not move. Do not merge them into a composite blocklist key. Check them as an invariant.

Token design that survives per-request checks

If the second checkpoint is going to exist, it has to be cheap enough to run on every object.

The industry has converged, independently across several CDNs, on a two-tier model: a short-lived entry token authorizes the manifest, and the edge issues a longer session token that covers playlists, keys and segments for the duration of the session. The important property is that per-request verification is stateless. It is a signature check over claims carried in the request, not a lookup. HMAC-SHA256 is microseconds; an RS256 verify is on the order of 50 to 100 microseconds. State appears only in the revocation path.

The cost that actually matters is invocation overhead, not crypto. On CloudFront, a Function runs in sub-millisecond time at roughly $0.10 per million invocations, while Lambda@Edge is around $0.60 per million plus duration and shows warm latencies in the tens of milliseconds. That difference decides whether you can afford to run this on segments or only on manifests. Run manifest rewriting in the heavyweight runtime if you must; keep the per-segment path in the lightweight one.

There is now a standard worth knowing about rather than inventing your own format: CAT, standardized as CTA-5007, a CWT/COSE-signed CBOR token. Three of its claims map directly onto the problems above:

  • catnip binds the token to an IP or prefix
  • catr carries renewal instructions, so the edge can mint a refreshed token near expiry without a round trip to your auth service
  • catif expresses a conditional action, for example redirect to re-authentication instead of a hard denial

Akamai’s EdgeWorkers, Fastly Compute and CloudFront Functions all have implementations. If a third-party CDN is ever going to sit in front of you, a standard token is the difference between a configuration change and a rewrite.

Binding to an IP without breaking real users

Binding a session to an address is the single highest-value control here, and the fastest way to cause an outage for legitimate users. The rules are not subtle:

  • Never bind to an exact address. Bind to a prefix: /24 for IPv4, and never narrower than /64 for IPv6, realistically /56, because privacy extensions rotate the interface identifier.
  • CGNAT is everywhere. RFC 6598 reserves 100.64.0.0/10, and RFC 6888 contemplates allocations as small as 512 ports per subscriber, so hundreds of real customers can share one public IPv4. Cloudflare has reported that CGNAT addresses get rate-limited roughly three times as often as others despite showing effectively identical abuse rates. That is a pure false-positive tax.
  • Dual-stack clients move between address families mid-session under Happy Eyeballs (RFC 8305). If you authorize the v4 address and the next connection arrives over v6, you have locked out your own user.
  • iCloud Private Relay egresses through CDN address space and rotates. Apple publishes the egress ranges; if you are making decisions on datacenter-looking addresses, you need that list or you will mass-ban iPhone Safari.
  • Prefer a step-up to a block. A catif-style redirect to re-authentication turns a false positive from an outage into a minor annoyance.

One honest caveat: there are no published false-positive rates for IP-bound tokens from any CDN or operator. The guidance above is qualitative. Anyone quoting you a precise percentage is quoting a number they cannot support. Instrument your own traffic in monitoring mode and derive your own thresholds before enforcing anything.

The cache is where this gets dangerous

Suppose you now want to respond differently to a suspicious caller - throttle, degrade quality, serve a stale object. There is a trap here that is easy to walk into and very unpleasant to debug.

RFC 9111 defines the cache key as, at minimum, the request method and target URI. Your edge cache is shared. If you serve a degraded response for a flagged caller under the shared URL key, and it is cached, the next legitimate user gets the punishment. You have poisoned your own cache with your own countermeasure.

  Wrong                              Right
  -----                              -----
  request -> countermeasure          request -> cache lookup
          -> written to cache                -> clean object stays intact
          -> next user gets it               -> substitute on the way out
                                             -> private, no-store
                                             -> never written back

Three rules follow:

  1. Decide after the cache lookup and substitute on egress. The shared object stays pristine. This is the only approach that scales to per-caller decisions without collapsing hit ratio.
  2. Never put a raw fingerprint into the cache key. Quantize the decision to a low-cardinality label such as trust=good|suspect before it touches the key. Two values doubles your object count; a raw fingerprint multiplies it by your user count.
  3. Normalize unknown query parameters out of the cache key. Otherwise a caller appends ?cb=<random>, forces a MISS on every request, and pushes both the load and any expensive countermeasure straight through to your origin. Cache-busting is how attackers route around cache-absorbed rate limiting.

On the choice of countermeasure itself: throttling and quality capping are cache-safe by construction, because they change timing and rate rather than bytes, and they are indistinguishable from ordinary congestion. Deliberately serving corrupted or stale payloads is implementable and has a certain appeal, but it has essentially no public engineering precedent and by far the worst false-positive blast radius. A wrongly flagged real viewer gets broken video. Reserve it, if you use it at all, for high-confidence repeat abuse.

The ceiling, stated plainly

Everything above raises cost. None of it solves the case where somebody reimplements your client.

Fingerprinting asks: do you look like our client? An attacker holding your binary can copy the answer exactly. It is not a hard question for them; it is a specification.

The different question is: prove you are our client. On mobile that is platform attestation - Play Integrity on Android, App Attest on iOS - where the assertion is signed by the platform vendor over your signed binary, and possession of your APK does not help. It is the only mechanism in this post that a reimplemented client cannot satisfy by copying.

It is also partial. There is no equivalent on the web, on WebOS or on Tizen. Users on rooted devices lose access, which is a business decision rather than a technical one. And it belongs at token issuance rather than on the serving path, because running it per segment is neither affordable nor necessary.

Behavioural analysis deserves the same honesty. Request cadence, playlist polling regularity against the RFC 8216 timing rules, rendition switching entropy and the ratio of media-seconds requested to wall-clock-seconds are excellent at separating a downloader from a player. They are close to useless against a reimplemented client that is genuinely playing video to a genuine viewer, because its behaviour is not an imitation of legitimate behaviour. It is legitimate behaviour.

Detection without an executor is just a report

One more architectural point, and it is the one most often missed.

Suppose you detect abuse thirty minutes into a two-hour event. What stops it? If the client already holds everything it needs, the answer is nothing. You can block the next session. This one runs to the end.

You need a recurring checkpoint where a decision can be applied. Short token lifetimes with renewal give you one. If you are already running DRM, license renewal gives you a better one, because it is tamper resistant in a way an application-level heartbeat is not: without a fresh license there is no decryption, regardless of what the client pretends. Typical renewal intervals sit in the 60 to 600 second range with a short grace period.

The critical distinction: renewal detects nothing. If nothing changed between two renewals, the renewal succeeds. It is not the guard who spots the intruder, it is the door that can be closed once someone else does. Without the door, spotting them produces a report rather than an outcome. Without a detector upstream, the door never closes.

Chain them and the design closes:

  short token TTL
      -> client must periodically return to the auth service
      -> attestation runs there
      -> no new token
      -> no license renewal
      -> playback stops within one renewal interval

What you actually buy

You do not eliminate abuse. You change its cost structure, and that is worth saying out loud to whoever is funding the work.

  Before:  1 credential  -> 500 consumers   invisible; concurrency sees 1 session
  After:   500 credentials -> 500 consumers  now your existing controls apply:
                                             per-account concurrency, token limits,
                                             attestation at issuance, anomaly detection

An invisible problem becomes a countable one. The abuser is still there, but now every additional consumer costs them something, and they are operating on terrain where the controls you already built finally have something to act on.

Lessons learned

  • The ratio matters more than the checks. Counting how many requests are authorized versus how many are served tells you more about your posture than any list of controls.
  • Fingerprints are classifiers, not identities. Many addresses per fingerprint is normal. Many addresses per session is not. Almost every bad design confuses these two.
  • The invariant check beats the blocklist. “Has this session changed in a way a real session does not change” has a far better signal-to-false-positive ratio than “is this on a list”, and needs no list to maintain.
  • The IP is the only field you did not let the caller choose. Protect that property deliberately, at both the network and the application layer, and write a test that fails if a forwarding header is ever trusted from a non-local peer.
  • Countermeasures live after the cache lookup. Everything else eventually poisons your own cache.
  • Measure before enforcing. There are no published false-positive baselines for any of this. Monitoring mode on one channel for a week is worth more than any vendor benchmark.
  • A detector without an executor produces reports. Budget for the kill switch in the same sprint as the detection, or you will ship an excellent dashboard.

If I were redesigning today

I would stop treating the session identifier as a credential. It should be an opaque handle to server-side state, and every request that costs real bytes should carry a signed, short-lived, stateless token that the edge can verify without a lookup - CAT if a third-party CDN might ever be involved, a plain HMAC scheme if not.

I would put the trust decision in one function, called from exactly one place in the serving path, returning a low-cardinality label rather than a boolean. Everything downstream - cache key, countermeasure selection, telemetry - reads that label. That single choice makes the cache problem tractable and keeps the blast radius of a bad rule to something you can reason about.

And I would build the monitoring pipeline before the enforcement path. Distinct addresses per session, distinct sessions per account, media-seconds versus wall-clock, fingerprint stability within a session. All four are computable from access logs you are already writing, they require no changes to the request path, and they will tell you within days whether you have a problem worth funding and which of the three consumer types you are actually dealing with. That last question determines everything else, and it is remarkable how often it gets answered by assumption.
